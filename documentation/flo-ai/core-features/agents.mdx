## Creating Agents

Agents are the core building blocks of Flo AI. They represent AI-powered entities that can process inputs, use tools, and generate responses.

### AgentBuilder Methods

The `AgentBuilder` class provides a fluent interface for configuring agents. All methods return `self` for method chaining. Here's a complete reference:

| Method | Description | Parameters |
|--------|-------------|------------|
| `with_name(name: str)` | Set the agent's name | `name`: Display name for the agent |
| `with_prompt(system_prompt: str \| AssistantMessage)` | Set the system prompt | `system_prompt`: Instructions defining agent behavior |
| `with_llm(llm: BaseLLM)` | Configure the LLM provider | `llm`: Instance of OpenAI, Anthropic, Gemini, etc. |
| `with_tools(tools: List[Tool])` | Add tools to the agent | `tools`: List of Tool objects, ToolConfig, or tool dicts |
| `add_tool(tool: Tool, **prefilled_params)` | Add a single tool with optional pre-filled parameters | `tool`: Tool object, `**prefilled_params`: Parameters to pre-fill |
| `with_reasoning(pattern: ReasoningPattern)` | Set reasoning pattern | `pattern`: `REACT`, `COT`, `PLAN_EXECUTE`, or `DIRECT` |
| `with_retries(max_retries: int)` | Set maximum retry attempts | `max_retries`: Number of retries on failure (default: 3) |
| `with_max_tool_calls(max_tool_calls: int)` | Set how many tool calls one run may make | `max_tool_calls`: Tool call limit (default: 5) |
| `with_interactive(interactive: bool = True)` | Mark the agent as talking to a person turn by turn | `interactive`: see [Interactive Agents](#interactive-agents-chat-sessions) |
| `with_output_schema(schema: Dict \| Type[BaseModel])` | Set structured output schema | `schema`: Pydantic model class or JSON schema dict |
| `with_role(role: str)` | Set the agent's role | `role`: Internal role description |
| `with_actas(act_as: str)` | Set how agent presents itself | `act_as`: Message role (e.g., 'assistant', 'user') |
| `build()` | Create and return the configured Agent | Returns: `Agent` instance |

**Note:** `with_llm()` is required before calling `build()`. All other methods are optional.

### Basic Agent Creation

Create a simple conversational agent:

```python
from flo_ai.agent import AgentBuilder
from flo_ai.llm import OpenAI

agent = (
    AgentBuilder()
    .with_name('Customer Support')
    .with_prompt('You are a helpful customer support agent.')
    .with_llm(OpenAI(model='gpt-4o-mini'))
    .build()
)

response = await agent.run('How can I reset my password?')
```

## Agent Capabilities

### Variable Resolution

Use dynamic variables in agent prompts:

```python
agent = (
    AgentBuilder()
    .with_name('Personalized Assistant')
    .with_prompt('Hello <user_name>! You are <user_role> at <company>.')
    .with_llm(OpenAI(model='gpt-4o-mini'))
    .build()
)

# Use variables at runtime
variables = {
    'user_name': 'John',
    'user_role': 'Data Scientist',
    'company': 'TechCorp'
}

response = await agent.run(
    'What should I focus on today?',
    variables=variables
)
```

Placeholders are filled in the system prompt and in the user-side inputs of the run that receives the variables. Text already in the conversation (earlier replies, tool calls, tool results, another agent's output) is sent as stored, so angle brackets in it are just text. For an agent that talks to a person, whose messages should never be read as templates, see [Interactive Agents](#interactive-agents-chat-sessions).

### Conversation History

Agents automatically maintain conversation history across multiple interactions. The `run()` method returns the complete conversation history as a list of messages.

```python
agent = (
    AgentBuilder()
    .with_name('Chat Assistant')
    .with_prompt('You are a helpful assistant.')
    .with_llm(OpenAI(model='gpt-4o-mini'))
    .build()
)

# First interaction
response1 = await agent.run('Hello, my name is Alice.')
print(f"Response: {response1[-1].content}")  # Get last message

# Second interaction - agent remembers the conversation
response2 = await agent.run('What is my name?')
print(f"Response: {response2[-1].content}")  # Agent knows the name is Alice

# Access full conversation history
for message in agent.conversation_history:
    print(f"{message.role}: {message.content}")
```

#### Accessing Conversation History

The conversation history is stored in the `conversation_history` attribute:

```python
# Get all messages
all_messages = agent.conversation_history

# Get the last message
last_message = agent.conversation_history[-1]

# Filter messages by role
from flo_ai.models import UserMessage, AssistantMessage

user_messages = [
    msg for msg in agent.conversation_history 
    if isinstance(msg, UserMessage)
]

assistant_messages = [
    msg for msg in agent.conversation_history 
    if isinstance(msg, AssistantMessage)
]
```

#### Clearing History

Clear the conversation history to start a new conversation:

```python
# Clear all conversation history
agent.clear_history()

# Now the agent starts fresh
response = await agent.run('Hello!')
```

#### Manual History Management

You can manually add messages to the conversation history:

```python
from flo_ai.models import UserMessage, AssistantMessage

# Add a user message
agent.add_to_history(UserMessage('Previous context'))

# Add multiple messages at once
agent.add_to_history([
    UserMessage('Message 1'),
    AssistantMessage('Response 1'),
    UserMessage('Message 2')
])
```

## Advanced Features

### Reasoning Patterns

Configure agents to use different reasoning patterns:

```python
from flo_ai.agent import ReasoningPattern

# ReACT pattern - for tool-using agents that need structured reasoning
react_agent = (
    AgentBuilder()
    .with_name('ReACT Agent')
    .with_prompt('You solve problems step by step.')
    .with_llm(OpenAI(model='gpt-4o'))
    .with_tools([get_weather.tool])
    .with_reasoning(ReasoningPattern.REACT)
    .build()
)

# Chain of Thought pattern - for complex reasoning tasks
cot_agent = (
    AgentBuilder()
    .with_name('CoT Agent')
    .with_prompt('You think through problems carefully.')
    .with_llm(OpenAI(model='gpt-4o'))
    .with_tools([get_weather.tool])
    .with_reasoning(ReasoningPattern.COT)
    .build()
)

# Direct pattern (default) - for straightforward tasks
direct_agent = (
    AgentBuilder()
    .with_name('Direct Agent')
    .with_prompt('You provide direct answers.')
    .with_llm(OpenAI(model='gpt-4o'))
    .with_reasoning(ReasoningPattern.DIRECT)
    .build()
)

# Plan-and-execute pattern - for multi-step tasks
planning_agent = (
    AgentBuilder()
    .with_name('Planning Agent')
    .with_prompt('You research questions thoroughly.')
    .with_llm(OpenAI(model='gpt-4o'))
    .with_tools([get_weather.tool])
    .with_reasoning(ReasoningPattern.PLAN_EXECUTE)
    .with_max_tool_calls(15)
    .build()
)
```

### Plan-and-Execute

With `ReasoningPattern.PLAN_EXECUTE` the agent writes a plan before it starts and keeps it up to date as it works. The agent is given an `update_plan` tool for this automatically; you do not add it yourself.

- The plan is a list of steps, each `pending`, `in_progress`, `completed`, or `skipped`. The agent sends the whole list on every update.
- The agent's reply is accepted as its final answer once every step is `completed` or `skipped`. If it replies while steps are unfinished, it is shown the plan and asked to continue.
- A request that needs no steps is answered directly, without a plan.
- Plan updates are not counted against `max_tool_calls`.
- The plan lasts for one `run`. Read it afterwards from `agent.plan` (`agent.plan.steps`, `agent.plan.render()`).

### Agents as Tools (Supervisor)

Any agent can be handed to another agent as a tool with `as_tool()`. The calling agent delegates a task, the result comes back to it, and it decides what to do next. This is how to build a supervisor over a group of specialists, and it needs no workflow edges or routers.

```python
researcher = AgentBuilder().with_name('researcher').with_prompt('You find facts.').with_llm(llm).with_tools([search.tool]).build()
analyst = AgentBuilder().with_name('analyst').with_prompt('You analyse data.').with_llm(llm).build()

supervisor = (
    AgentBuilder()
    .with_name('supervisor')
    .with_prompt('Delegate the work to your specialists and combine their results.')
    .with_llm(llm)
    .with_tools([
        researcher.as_tool('Finds facts and figures'),
        analyst.as_tool('Analyses figures you give it'),
    ])
    .with_reasoning(ReasoningPattern.PLAN_EXECUTE)
    .with_max_tool_calls(20)
    .build()
)

result = await supervisor.run('How did revenue change last quarter, and why?')
```

- Each delegation starts the worker from an empty conversation. It sees only the `task` text, so the supervisor must put all needed context in it.
- The supervisor sees only the worker's final answer, not its intermediate tool calls.
- If a worker fails, the supervisor receives the failure as the tool result and can work around it. A guardrail block stops the whole run.
- If a worker's prompt uses `<variables>`, they are filled in from the variables passed to the supervisor's `run`.
- The supervisor is a normal agent, so it can be a single node in an Arium workflow.
- Raise `max_tool_calls` for supervisors; the default of 5 is low for delegated work.

#### Delegating in parallel

Add `parallel_agents_tool` to let the supervisor hand out several independent tasks in one call:

```python
from flo_ai.tool import parallel_agents_tool

supervisor = (
    AgentBuilder()
    .with_name('supervisor')
    .with_prompt('Delegate the work to your specialists and combine their results.')
    .with_llm(llm)
    .with_tools([
        researcher.as_tool('Finds facts and figures'),
        analyst.as_tool('Analyses figures you give it'),
        parallel_agents_tool([researcher, analyst]),
    ])
    .build()
)
```

The supervisor calls `delegate_parallel` with a list of `{agent, task}` pairs and gets all the answers back together. Tasks for different agents run at the same time; two tasks for the same agent in one call run one after the other.

#### In a YAML workflow

In an Arium YAML file, list other agents of the same workflow under an agent's `tools:`. They become its delegation tools, and with two or more of them `delegate_parallel` is added automatically:

```yaml
arium:
  agents:
    - name: supervisor
      job: Delegate the work to your specialists and combine their results.
      settings:
        reasoning_pattern: PLAN_EXECUTE
        max_tool_calls: 20
      tools:
        - researcher                      # described by the researcher's role
        - name: analyst
          description_override: Analyses figures you give it
    - name: researcher
      role: a researcher who finds facts and figures
      job: Find the facts you are asked for.
    - name: analyst
      job: Analyse the figures you are given.
  workflow:
    start: supervisor
    edges: []
    end: [supervisor]
```

- An agent that is only delegated to is not a workflow node, so it needs no edges.
- An agent can be both a delegate and a workflow step.
- Agents may be listed in any order. Agents that delegate to each other in a cycle are rejected.
- If a name is both an agent and an entry in the tool registry, the registered tool is used.

### Tool Calls in History

When an agent calls a tool, the conversation records both sides of it: an `AssistantMessage` whose `tool_calls` holds the tool name and arguments, followed by a `FunctionMessage` with the result.

```python
from flo_ai.models import AssistantMessage, FunctionMessage, ToolCall

history = await agent.run('Create a workflow called onboarding')

# history now contains, in order:
#   AssistantMessage(content='', tool_calls=[ToolCall(name='create_workflow',
#                                                     arguments={'name': 'onboarding'}, id='...')])
#   FunctionMessage(name='create_workflow', content='...', tool_call_id='...')
#   AssistantMessage(content='Done.')
```

A stored conversation can be passed back in as `inputs` to continue it, tool calls included:

```python
agent = build_agent()          # a fresh instance, e.g. on the next request
await agent.run([*stored_messages, UserMessage(content='Now add a reviewer step')])
```

- `ToolCall.id` and `FunctionMessage.tool_call_id` carry the provider's id for the call where it issues one (Anthropic, Bedrock), and are `None` otherwise.
- OpenAI, Azure OpenAI, vLLM, Anthropic, Bedrock, Gemini and Vertex AI are sent the recorded call. Ollama and RootFlo have no slot for it in the way flo-ai formats their messages, so they are sent the result only.
- A call that has no result after it (a run that was cut short) is not sent; only its text is.

### Agent Events

Pass `on_event` to `run` to be told about each step as it happens, for streaming progress to a UI or saving a conversation as it grows:

```python
from flo_ai.agent import AgentEvent, AgentEventType

async def on_event(event: AgentEvent) -> None:
    if event.type == AgentEventType.TOOL_CALL:
        call = event.message.tool_calls[0]
        print(f'calling {call.name}({call.arguments})')
    elif event.type == AgentEventType.TOOL_RESULT:
        print(f'{event.message.name} returned')
    elif event.type == AgentEventType.MESSAGE and event.is_final:
        print(event.message.content)
    await save(event.message)

await agent.run('Create a workflow called onboarding', on_event=on_event)
```

| Event type | `event.message` | When |
|---|---|---|
| `tool_call` | `AssistantMessage` with `tool_calls` | The model asked for a tool, before it runs |
| `tool_result` | `FunctionMessage` | The tool returned or failed |
| `message` | `AssistantMessage` | The model replied; `is_final` marks the answer |
| `notice` | `UserMessage` or `AssistantMessage` | The agent told the model to keep going, or recorded an error before a retry |

- The events of a run, in order, are exactly the messages it added to the conversation after the caller's inputs. Saving each `event.message` saves the turn.
- The callback may be sync or async. An exception it raises is logged and does not stop the run.
- Events come from the agent you call. Agents it delegates to through tools do not report to this callback; their work appears as the `tool_result`.
- If a guardrail blocks the turn, `run` raises and the agent's own history is rolled back; events already delivered for that turn should be discarded.

### Interactive Agents (Chat Sessions)

Set `interactive` when a person is on the other end of the agent, turn by turn: a chat UI, a support assistant, a session that sets things up for the user. Leave it off for agents that run a task and return a result, and for agents inside workflows.

```python
agent = (
    AgentBuilder()
    .with_name('assistant')
    .with_prompt('You help users manage their orders.')
    .with_llm(llm)
    .with_tools([get_order_status.tool, cancel_order.tool])
    .with_interactive()
    .build()
)
```

It can also be passed to the constructor (`Agent(..., interactive=True)`), set on a built agent (`agent.interactive = True`), or set in YAML:

```yaml
agent:
  name: assistant
  job: You help users manage their orders.
  settings:
    interactive: true
```

#### What it changes

| | Default | Interactive |
|---|---|---|
| A text reply with no tool call, from an agent that has tools | Checked by a second LLM call. If judged unfinished, the agent is told to keep going (up to 3 times) | Ends the turn at once and is returned |
| What the user typed | A template: `<name>` must have a matching variable, or the run fails | Taken as written. `How do I centre a <div>?` needs no variables |
| The system prompt | A template | A template (unchanged) |
| `PLAN_EXECUTE` with unfinished steps | A text reply is sent back with the plan and a request to continue | A text reply still ends the turn |

The first row is the reason the option exists. When an interactive agent asks "Which order do you mean?", that question is its reply, and the person answers it in the next turn. Without the option, the question is treated as unfinished work.

In every mode, text already in the conversation (earlier replies, tool calls, tool results) is sent as stored and is never treated as a template.

#### A turn, from the calling application's side

The agent does not store sessions. The application that calls it owns the conversation: it saves messages, passes them back on the next turn, and shows the reply.

```python
from flo_ai.models import UserMessage

async def handle_turn(session_id: str, user_text: str) -> str:
    stored = await load_messages(session_id)          # everything saved so far
    new_message = UserMessage(content=user_text)
    await save_message(session_id, new_message)

    agent = build_agent()                             # a fresh instance per turn
    agent.interactive = True

    async def on_event(event):
        await save_message(session_id, event.message) # tool calls, results, the reply
        await push_to_ui(session_id, event)

    history = await agent.run([*stored, new_message], on_event=on_event)
    return history[-1].content
```

What the application should do:

- **Pass the stored conversation back in, with the new message last.** Include the tool-call and tool-result messages, not only the text. See [Tool Calls in History](#tool-calls-in-history).
- **Do not pass the user's text through `variables`,** and do not pre-escape angle brackets. Pass variables only for placeholders in the system prompt.
- **Save from `on_event`.** Each event carries one message the turn added, in order. Save `tool_call`, `tool_result` and `message` events. A `notice` is the agent's own note to the model; with `interactive` there are none in the normal flow, but one can appear when a failed step is retried. Keep it out of what the user sees.
- **Treat every final message the same way: show it and wait for the user.** The agent does not say whether its reply is an answer or a question, and the application does not need to know. Whatever the user sends next is passed in as the next turn.
- **Show progress from events.** A turn with several tool calls can take a while. `tool_call` events arrive before each tool runs and are the natural "Looking up your order…" signal. The reply text arrives whole, not token by token.
- **Start each turn from stored messages.** Build the agent per turn, or call `clear_history()` first, so the conversation comes from storage and nothing is duplicated.
- **Keep a call and its result together when trimming.** If you send only the most recent messages, cut at a user message. A tool result without its call, or a call without its result, makes providers reject the request. (A call left unanswered at the very end, from a turn that was cut short, is handled for you: only its text is sent.)

#### Errors to handle

| Raised by `run` | Meaning | What to do |
|---|---|---|
| `GuardrailBlocked` | A guardrail policy blocked the turn. The agent's history is rolled back | Discard what `on_event` delivered for this turn, and show a policy message |
| `ModelRefusedError` | The provider's safety system declined the request. Has `category` and `explanation` | Show a refusal message. Retrying the same request gives the same result |
| `AgentError` | A tool or the model failed and retries ran out | Show a failure message; the user's message is already saved, so they can retry |

A failed tool is always recorded as the result of its call before the error is raised, so a conversation saved up to that point is still valid to continue.

#### Things to know

- **Tool limit.** If a turn uses up `max_tool_calls`, the agent is asked for a final answer from what it has. Raise the limit for assistants that do multi-step work.
- **Planning.** `interactive` can be combined with `PLAN_EXECUTE`. The plan guides the work, but it no longer holds the turn open, and it is reset at the start of each `run`. An agent built per turn starts with no plan; the earlier `update_plan` calls are in the history for the model to pick up from.
- **Delegated agents.** Agents used as tools by an interactive agent are not interactive themselves. They cannot ask the user anything; they return a result to the agent that called them.
- **Workflows.** Do not set `interactive` on agents that are nodes in an Arium workflow. A workflow passes each node's reply to the next node, not to a person.
